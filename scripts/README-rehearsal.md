# Devnet rehearsal

Запускайте из корня проекта. Это сквозная проверка с реальными транзакциями только в Solana devnet; mainnet не поддерживается.

```powershell
npm run devnet:wallet
npm run rehearsal
```

`devnet:wallet` создаёт `.env.devnet.local` с `DEVNET_KEYPAIR_JSON` один раз, без перезаписи существующего файла. Перед выводом публичного адреса ключ записывается и считывается обратно. Файл исключён из Git и содержит закрытый ключ: не публикуйте его. Заданный извне `DEVNET_KEYPAIR_JSON` имеет приоритет; сохранность такого значения обеспечивает его владелец. Без настроенного ключа rehearsal отказывается запускаться.

Сценарий создаёт новые DBC config, SPL-токен с шестью decimals и WSOL-пул с порогом миграции 0.1 test SOL, постоянной комиссией DBC 1%, без token vesting и с 100% partner LP в permanent lock. Затем он покупает и продаёт токен на DBC, достигает порога, мигрирует в DAMM v2, выполняет покупку на DAMM v2 и проверяет фактически полученный баланс токенов. Котировки используют slippage 1%; preflight транзакций включён. Новые on-chain программы не разворачиваются.

Перед каждой записью скрипт проверяет genesis hash Solana devnet и останавливается, если подтверждённые списания с payer уже достигли 0.5 test SOL. Бюджет суммирует положительные разницы `preBalances[0] − postBalances[0]` каждой своей транзакции, включая комиссии неуспешных транзакций; пополнение или поступление от продажи не уменьшает накопленную сумму. Неизвестный результат предыдущей транзакции блокирует новую запись, пока результат не выяснен или подпись не отсутствует после истечения blockhash. Это проверка перед транзакцией, а не гарантия максимального итогового списания. При обычном запуске, если у плательщика меньше 0.5 SOL, выполняется одна попытка запросить 1 test SOL у devnet faucet. Ошибка или ограничение faucet завершает прогон ошибкой, без имитации успешных транзакций.

Если публичный faucet недоступен, можно вручную пополнить настроенный кошелёк:

```powershell
npm run rehearsal:session
```

При недостаточном балансе этот режим не запрашивает airdrop. Он выводит публичный адрес настроенного devnet payer и ссылку [Solana faucet](https://faucet.solana.com/), затем проверяет баланс каждые 5 секунд, максимум 15 минут, ожидая не менее 0.5 test SOL. После неудачного или успешного прогона сессия ждёт команды `run` или `exit`; payer остаётся тем же. Новая попытка не запускается автоматически. После закрытия процесса ключ можно снова загрузить из локального environment-файла. Переводить mainnet SOL на этот адрес нельзя.

Для одноразового ожидания funding доступно `node --import tsx scripts/rehearsal.ts --wait-for-funding`. Этот процесс завершается после попытки; настроенный environment-файл сохраняется.

Команда `run` заново загружает entry script `rehearsal.ts`, позволяя подхватить его исправления без закрытия кошелька. Импортируемые зависимости остаются в кэше процесса.

Чтобы использовать свой отдельный профинансированный devnet-кошелёк, задайте переменные окружения:

- `DEVNET_RPC_URL` — RPC endpoint для devnet; genesis hash всё равно проверяется.
- `DEVNET_KEYPAIR_JSON` — JSON-массив из 64 байт закрытого ключа только для выделенного devnet-кошелька. Передавайте его через окружение; не записывайте ключ в исходники, историю терминала, отчёты или этот README.

Для продолжения уже созданного **пустого** тестового пула:

```powershell
$env:DEVNET_RESUME_POOL = '4KSYjPvfeQghULdKBD7r1T2naxCvLtknr3QET3VcuaGS'
npm run rehearsal:session
```

До funding и записей проверяются devnet, владельцы pool/config, PDA, SPL/SOL, параметры тестовой конфигурации и supply mint. Пул должен иметь нулевой резерв, без swaps и начавшейся миграции. Новый payer может выполнить сделки и миграцию; старый creator не подписывает их. Создание config/pool пропускается и явно не засчитывается как новые транзакции. Пул из примера выше уже мигрировал, поэтому повторный resume для него будет отклонён.

Если buy и sell подтверждены, но graduation ещё не отправлялась, задайте дополнительно `DEVNET_RESUME_EVIDENCE` с путём предыдущего rehearsal JSON. Он должен содержать ровно два подтверждённых шага dbc-buy/dbc-sell того же pool и payer. Скрипт перепроверит их receipts в сети, учтёт прежние расходы и начнёт с graduation без повторных buy/sell. Более поздние отправки отклоняются; это не универсальный recovery после любого этапа. Для нового запуска удалите обе переменные `DEVNET_RESUME_POOL` и `DEVNET_RESUME_EVIDENCE` из окружения.

Graduation использует SDK `swapQuote2`/`swap2` с `PartialFill`, slippage 1% и проверкой достижения порога. Это позволяет не расходовать часть заданного input сверх доступной кривой; обычный ExactIn для такой суммы возвращал Insufficient Liquidity.

Прогон сохраняет operational evidence в `artifacts/rehearsal-<timestamp>.json`. Подпись, blockhash и lastValidBlockHeight сохраняются **до** отправки подписанной транзакции; ошибка сохранения останавливает отправку. Timeout или ошибка отправки не доказывают, что транзакция не прошла: перед повтором проверьте её signature. Без resume каждый прогон создаёт новые адреса pool/mint/config. Session сохраняет payer и бюджет между попытками; бюджет и pending-состояние существуют только до завершения процесса. После перезапуска обязательно проверяйте evidence предыдущей попытки. Существующие тестовые аккаунты не удаляются.

RPC transport ограничивает частоту запросов к публичным Solana endpoints и повторяет чтения при HTTP/JSON-RPC `429` максимум два раза, с паузой и ограниченным timeout. Приложение не повторяет записывающие RPC-вызовы автоматически. Параметр Solana `maxRetries: 2` разрешает RPC повторно доставить ту же подписанную транзакцию валидатору.

После подтверждённых шагов `create-pool`, достижения порога и миграции скрипт дополнительно читает пул инспектором LaunchCheck и сохраняет три стандартных `InspectionReport` в файлы `artifacts/inspection-<timestamp>-pool-created.json`, `...-threshold-reached.json` и `...-migration-verified.json`. В каждом отчёте `source` — `live`, сеть — `devnet`, а адрес пула — фактический адрес созданного DBC pool. Пути перечислены отдельно в поле `inspectionReports` файла rehearsal evidence. Любой снимок можно импортировать в LaunchCheck как baseline и сравнить с новым чтением того же пула; невалидный отчёт, неверная стадия, адрес или неподтверждённый DAMM v2 pool прерывает rehearsal ошибкой.

Только `status: passed` означает, что весь цикл был выполнен и проверен, включая фактическую покупку на DAMM v2. Адреса, выведенные до подтверждённого `create-pool`, лишь вычислены; они не доказывают создание аккаунтов. Rehearsal имеет отдельную схему evidence; только файлы инспекции являются импортируемыми LaunchCheck reports.

При продолжении после сделок первый снимок называется `resume-start`, а buy/sell и создание относятся к предыдущим прогонам. Последний `passed` не означает, что все транзакции были отправлены одним процессом.

Это **не точное воспроизведение production-конфигурации**. Малый devnet-порог, quote-балансы, состояние аккаунтов и версии программ отличаются от условий mainnet. Это не аудит токена и не свидетельство органического спроса.

Вызовы SDK сверялись с установленными TypeScript declarations и исходниками, а также с официальными [migration tests](https://github.com/MeteoraAg/dynamic-bonding-curve-sdk/blob/main/packages/dynamic-bonding-curve/tests/migration.test.ts). Для ручной миграции есть официальный [Meteora Manual Migrator](https://migrator.meteora.ag/).
